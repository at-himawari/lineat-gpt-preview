# 要件定義書

## はじめに

本機能は、LINE チャットボットに Stripe 決済を統合した 2 段階の課金システムを実装します。システムは 2 つの独立した有料機能を提供します：(1) プレミアムユーザーが 1 日で 100 件のメッセージ制限を超えた場合のメッセージ枠の追加購入、(2) より高度な AI モデルへのアクセス。ユーザーはどちらか一方、または両方の機能を独立して購入できます。システムはメッセージ使用量の追跡、決済フローの管理、枠制限の適用、およびサブスクリプション状態に基づく AI モデルの切り替えを行います。

**重要な変更**: 現在は全ユーザーが 1 日 30 件の制限ですが、プレミアムプランのユーザーは 1 日 100 件、非プレミアムユーザーは 1 日 30 件の制限を持つように変更します。

## 用語集

- **システム**: 決済処理が統合された LINE チャットボットアプリケーション
- **ユーザー**: チャットボットと対話する LINE ユーザー
- **メッセージ枠**: プレミアムユーザーが 1 日の期間内に送信できるメッセージの数
- **基本枠**: プレミアムユーザーに 1 日ごとに提供される 100 件のメッセージ
- **追加枠**: 決済成功後に付与される追加のメッセージ枠
- **枠期間**: 最初のメッセージまたは枠リセットから始まる 1 日間のローリングウィンドウ
- **決済セッション**: 枠追加またはモデルアップグレード購入のために作成される Stripe Checkout セッション
- **Webhook**: LINE または Stripe からのイベントを受信する HTTP エンドポイント
- **基本モデル**: 標準的な会話に使用されるデフォルトの AI モデル（Gemini Flash）
- **プレミアムモデル**: サブスクリプションを通じて利用可能な高度な AI モデル（Gemini Pro）
- **モデルサブスクリプション**: プレミアムモデルへのアクセスを付与する有料機能
- **サブスクリプション状態**: ユーザーが現在アクティブなプレミアムモデルアクセスを持っているかを示す状態
- **商品タイプ**: 購入のタイプ - "quota_extension"（枠追加）または"model_upgrade"（モデルアップグレード）

## 要件

### 要件 1

**ユーザーストーリー:** プレミアムプランのユーザーとして、高品質なサービスを利用するために、1 日に最大 100 件のメッセージを送信したい。

#### 受入基準

1. WHEN プレミアムユーザーが最初のメッセージを送信する THEN システムは、ユーザーのメッセージカウントを 1 に初期化し、カウント期間の開始時刻を設定しなければならない
2. WHEN プレミアムユーザーがカウント期間内にメッセージを送信する THEN システムは、メッセージカウントを 1 増やさなければならない
3. WHEN カウント期間が 1 日を超える THEN システムは、ユーザーのメッセージカウントを 0 にリセットし、カウント期間を再開しなければならない
4. WHEN プレミアムユーザーのメッセージカウントが 100 未満である THEN システムは、メッセージを処理し、応答を生成しなければならない
5. WHEN プレミアムユーザーのメッセージカウントが 100 に達する THEN システムは、メッセージ処理を防止し、決済手順を提供しなければならない
6. WHEN 非プレミアムユーザーがメッセージを送信する THEN システムは、1 日 30 件のメッセージ制限を適用しなければならない

### 要件 2

**ユーザーストーリー:** メッセージ枠を超えたプレミアムユーザーとして、Stripe を通じて追加のメッセージを購入し、すぐにチャットボットを使い続けたい。

#### 受入基準

1. WHEN プレミアムユーザーが 100 件のメッセージ枠を超える THEN システムは、Stripe 決済リンクを含む LINE メッセージを送信しなければならない
2. WHEN システムが決済リンクを生成する THEN システムは、追加メッセージ枠商品を含む Stripe Checkout セッションを作成しなければならない
3. WHEN ユーザーが決済リンクをクリックする THEN システムは、ユーザーを Stripe Checkout ページにリダイレクトしなければならない
4. WHEN ユーザーが決済を正常に完了する THEN システムは、ユーザーの現在の枠に追加メッセージを付与しなければならない
5. WHEN ユーザーが決済をキャンセルする THEN システムは、ユーザーの現在の枠状態を変更せずに維持しなければならない

### 要件 3

**ユーザーストーリー:** システム管理者として、決済後すぐに枠拡張が適用されるように、Stripe webhook イベントでユーザー枠を自動更新したい。

#### 受入基準

1. WHEN Stripe が checkout.session.completed イベントを送信する THEN システムは、webhook 署名を検証しなければならない
2. WHEN webhook 署名が有効である THEN システムは、セッションメタデータからユーザー識別子を抽出しなければならない
3. WHEN ユーザー識別子が抽出される THEN システムは、ユーザーのメッセージ枠に追加メッセージを付与しなければならない
4. WHEN 枠更新が成功する THEN システムは、トランザクションをログに記録し、200 ステータスコードを返さなければならない
5. IF webhook 署名が無効である THEN システムは、リクエストを拒否し、401 ステータスコードを返さなければならない

### 要件 4

**ユーザーストーリー:** ユーザーとして、使用量を管理し、潜在的な決済を計画できるように、残りのメッセージ枠を知りたい。

#### 受入基準

1. WHEN ユーザーがメッセージを送信する THEN システムは、応答メタデータに残り枠数を含めなければならない
2. WHEN ユーザーの残り枠が 50 件未満になる THEN システムは、チャットボットの応答に枠警告を追加しなければならない
3. WHEN ユーザーの残り枠が 10 件から 50 件の間である THEN システムは、正確な残り件数を表示しなければならない
4. WHEN ユーザーの残り枠が 10 件未満になる THEN システムは、決済準備手順を含む緊急警告を表示しなければならない
5. WHEN ユーザーが明示的に枠情報を要求する THEN システムは、現在の枠、枠期間の残り時間、およびリセット日を応答しなければならない

### 要件 5

**ユーザーストーリー:** システム管理者として、収益を追跡し、決済を監査し、ユーザーサポートを提供できるように、決済トランザクションをデータベースに保存したい。

#### 受入基準

1. WHEN Stripe Checkout セッションが作成される THEN システムは、セッション ID、ユーザー ID、商品タイプ、金額、および作成タイムスタンプをデータベースに保存しなければならない
2. WHEN 決済が完了する THEN システムは、完了タイムスタンプと決済ステータスでトランザクションレコードを更新しなければならない
3. WHEN 決済が失敗またはキャンセルされる THEN システムは、失敗ステータスと理由でトランザクションレコードを更新しなければならない
4. WHEN トランザクション履歴を照会する THEN システムは、作成タイムスタンプの降順でレコードを取得しなければならない
5. WHEN トランザクションレコードが作成される THEN システムは、データの不整合を防ぐために、枠またはサブスクリプション更新とのアトミック性を確保しなければならない

### 要件 6

**ユーザーストーリー:** 開発者として、ユーザーが明確なフィードバックを受け取り、障害時にシステムが安定を保つように、決済フローの包括的なエラー処理を実装したい。

#### 受入基準

1. WHEN Stripe API 呼び出しが失敗する THEN システムは、エラーの詳細をログに記録し、ユーザーフレンドリーなエラーメッセージを返さなければならない
2. WHEN 決済処理中にデータベース操作が失敗する THEN システムは、部分的な変更をロールバックし、ユーザーに通知しなければならない
3. WHEN webhook イベントを処理できない THEN システムは、Stripe の再試行ロジックのために適切な HTTP ステータスコードを返さなければならない
4. WHEN Stripe 通信中にネットワークタイムアウトが発生する THEN システムは、指数バックオフを使用した再試行ロジックを実装しなければならない
5. IF ユーザーが複数の同時決済セッションを作成しようとする THEN システムは、重複セッションを防止し、既存のアクティブセッションを返さなければならない

### 要件 7

**ユーザーストーリー:** システム管理者として、異なる環境（開発、ステージング、本番）を安全に管理できるように、環境変数を介して Stripe 設定を構成したい。

#### 受入基準

1. WHEN システムが起動する THEN システムは、環境変数から Stripe API キーを読み込まなければならない
2. WHEN システムが Checkout セッションを作成する THEN システムは、環境変数から構成された成功 URL とキャンセル URL を使用しなければならない
3. WHEN システムが webhook イベントを受信する THEN システムは、環境変数からの webhook シークレットを使用して署名を検証しなければならない
4. WHEN 必要な Stripe 環境変数が欠落している THEN システムは、重大なエラーをログに記録し、決済機能を無効にしなければならない
5. WHERE 環境が開発である THEN システムは、Stripe テストモード認証情報を使用し、追加のデバッグ情報をログに記録しなければならない

### 要件 8

**ユーザーストーリー:** プレミアムユーザーとして、追加枠を購入する際に未使用のメッセージを失わないように、枠拡張を既存の枠に積み重ねたい。

#### 受入基準

1. WHEN プレミアムユーザーが枠拡張を購入する THEN システムは、現在の残り枠に追加メッセージを付与しなければならない
2. WHEN プレミアムユーザーが 50 件使用済みで、拡張を購入する THEN システムは、使用カウントをリセットまたは調整しなければならない
3. WHEN プレミアムユーザーが枠期間内に複数の拡張を購入する THEN システムは、購入されたすべての枠を累積しなければならない
4. WHEN 枠期間がリセットされる THEN システムは、以前の購入に関係なく、カウントを 0 にリセットしなければならない
5. WHEN 枠拡張が適用される THEN システムは、枠期間のリセット時刻を変更してはならない

### 要件 9

**ユーザーストーリー:** ユーザーとして、より高品質な会話とより優れた推論能力を得るために、より高度な AI モデルへのアクセスを購入したい。

#### 受入基準

1. WHEN ユーザーがモデルアップグレード情報を要求する THEN システムは、プレミアムモデルの機能と価格を説明する LINE メッセージを送信しなければならない
2. WHEN システムがモデルアップグレード決済リンクを生成する THEN システムは、プレミアムモデルサブスクリプション商品を含む Stripe Checkout セッションを作成しなければならない
3. WHEN ユーザーがモデルアップグレード決済を完了する THEN システムは、そのユーザーのプレミアムモデルアクセスを有効化しなければならない
4. WHEN ユーザーがプレミアムモデルアクセスを持つ THEN システムは、その後のすべての会話にプレミアムモデルを使用しなければならない
5. WHEN プレミアムモデルアクセスを持たないユーザーがメッセージを送信する THEN システムは、基本モデルを使用しなければならない

### 要件 10

**ユーザーストーリー:** プレミアムモデルアクセスを持つユーザーとして、3 日ごとにモデルアクセスを再購入する必要がないように、サブスクリプションを枠期間を超えて永続化したい。

#### 受入基準

1. WHEN ユーザーがプレミアムモデルアクセスを購入する THEN システムは、有効化タイムスタンプとともにサブスクリプション状態を保存しなければならない
2. WHEN 枠期間がリセットされる THEN システムは、ユーザーのプレミアムモデルサブスクリプション状態を維持しなければならない
3. WHEN プレミアムモデルアクセスを持つユーザーがメッセージを送信する THEN システムは、プレミアムモデルを使用する前にサブスクリプションがアクティブであることを確認しなければならない
4. WHEN ユーザー情報を照会する THEN システムは、枠状態とモデルサブスクリプション状態の両方を含めなければならない
5. WHEN プレミアムモデルサブスクリプションが有効化される THEN システムは、アプリケーションの再起動を超えて状態を永続化しなければならない

### 要件 11

**ユーザーストーリー:** システム管理者として、各決済タイプを正しく処理できるように、枠拡張とモデルアップグレードの購入を区別したい。

#### 受入基準

1. WHEN Stripe Checkout セッションを作成する THEN システムは、セッションメタデータに商品タイプを含めなければならない
2. WHEN webhook イベントを処理する THEN システムは、セッションメタデータから商品タイプを読み取らなければならない
3. WHEN 商品タイプが"quota_extension"である THEN システムは、ユーザーの枠に追加メッセージを付与しなければならない
4. WHEN 商品タイプが"model_upgrade"である THEN システムは、ユーザーのプレミアムモデルアクセスを有効化しなければならない
5. IF 商品タイプが認識されない THEN システムは、エラーをログに記録し、400 ステータスコードを返さなければならない

### 要件 12

**ユーザーストーリー:** ユーザーとして、枠拡張とモデルアップグレードの間で選択できるように、現在のニーズに基づいて異なる決済オプションを受け取りたい。

#### 受入基準

1. WHEN ユーザーがメッセージ枠を超える THEN システムは、枠拡張のみの決済リンクを送信しなければならない
2. WHEN ユーザーがモデルアップグレードを要求する THEN システムは、プレミアムモデルサブスクリプションのみの決済リンクを送信しなければならない
3. WHEN ユーザーが決済オプションを表示するコマンドを送信する THEN システムは、価格とともに枠拡張とモデルアップグレードの両方のオプションを表示しなければならない
4. WHEN 決済オプションを表示する THEN システムは、ユーザーが現在アクティブにしている機能を示さなければならない
5. WHEN ユーザーがすでにプレミアムモデルアクセスを持ち、アップグレードを要求する THEN システムは、ユーザーがすでにアクセスを持っていることを通知しなければならない
